ConceptsSlots, destinations and files

Three levels describe where a certificate goes on a server.

LevelWhat it isTypical count
SlotOne certificate as the server sees it. A deployment target in the app names one slot.One per certificate, for example reddin-wildcard.
DestinationOne program that uses the certificate: a folder and file names, or a TSplus import, plus what to restart.One per program instance.
FileA source (the format, such as fullchain) and the file name to give it.One to three per destination.

The app never decides folders or file names for an agent. It asks the agent which sources the slot needs and sends those. When you add a NetTalk instance or change a file name, you change agent.json on the server and nothing in the app.

One agent can hold many slots. Two certificates deployed to the same server are two slots in the same file, and two targets in the app (one on each certificate) pointing at the same agent URL.

ConceptsHow a deployment runs

The order matters when you write commands, so here it is exactly as the agent runs it.

1 · Ask

The app calls GET /api/slots/{slot} and gets the list of sources the slot needs.

↓
2 · Send

The app builds those files from the issued certificate and posts them in Base64 to /api/deploy, with the PFX password only when a pfx, p12 or encrypted-key is needed.

↓
3 · Admit

The agent re-reads agent.json, checks AllowedIps and the API key. Deployments run one at a time.

↓
4 · Write

For each destination in order: back up the current file, write the new one atomically. TSplus destinations import instead.

↓
5 · Services

Every RestartServices entry of the successful destinations, each service once, in the order first listed.

↓
6 · Programs

Every RestartPrograms entry (Windows), each executable once.

↓
7 · Commands

Each destination's Commands in order, with {folder} replaced, then the slot's own Commands.

↓
8 · Report

Every step, good or bad, goes back to the app's activity log and into agent.log.

Commands run after all restarts

A destination's Commands do not run right after its own files are written; they run after every destination has been written and every service restarted. If a command must happen before a restart, leave RestartServices empty and do both in one command, for example icacls … && net stop X && net start X.

When a step fails

A failed step does not stop the run. If writing a destination fails, that destination's restarts and commands are skipped, and the other destinations carry on. A failed restart or a command with a non-zero exit code is reported, and the next step still runs. The deployment is then marked failed in the app, with every step listed, so you can see which part worked.

ConceptsEditing agent.json on a live server

The agent reads agent.json again on every request. A new slot, destination or file name applies to the next deployment without a restart. Only Port is read at start-up; after changing it, restart the service and open the new port in the firewall.

A syntax error does not stop the service. Requests are refused with a clear message, which the app shows, until the file is fixed. check prints the line:

ERROR agent.json has a syntax error on line 14 (at $.Slots[0].Destinations[0].Folder):
        "Folder": "C:\Apps\Web\certificates",
Common causes: text not inside "quotes", curly quotes instead of straight ", a missing comma between items,
or a comma after the last item. Backslashes in Windows paths must be doubled (C:\\Apps).

FilesHow files are written

  • Atomically. Each file is written to <name>.cg-tmp and then renamed over the old one, so a program never reads half a file.
  • Folders are created when they do not exist.
  • Linux, new files: key material (combined, combined-keyfirst, encrypted-key, jks, k8s, key, p12, pfx) gets mode 600; other files get 644.
  • Linux, replaced files keep the owner, group, mode and SELinux label of the file they replace (chown --reference, chcon --reference). A Cockpit certificate set to root:cockpit-ws 640 stays that way.
  • Windows files inherit the folder's permissions.

FilesBackups

Before a file is replaced, the current one is copied into the agent's own folder, never next to the live files. HAProxy loads every file in its certificate folder, so a .bak there would be served too.

<agent folder>/backups/<slot>/<destination>/<yyyyMMdd-HHmmss>/<file>
C:\Program Files\CertificateGet Agent\backups\reddin-wildcard\NetTalk_-_Portal\20260927-031200\portal.crt

KeepBackups (default 5) is how many of those dated folders are kept per destination; 0 turns backups off. To roll back, copy the files from a dated folder back into place and restart the program, or run the destination's command by hand.

RestartsServices, programs and commands

RestartServices

On Windows, the service is stopped (waiting up to 90 seconds), then started (waiting up to 90 seconds for Running). On Linux, the agent runs systemctl restart <unit>. Each name is restarted once per deployment, even when several destinations list it.

Reload rather than restart where you can

A restart drops open connections. For HAProxy and nginx, leave RestartServices empty and use a Commands entry that checks the configuration and reloads, for example haproxy -c -f /etc/haproxy/haproxy.cfg && systemctl reload haproxy.

RestartPrograms

For programs that run on a desktop instead of as a service, such as a NetTalk server started from the Startup folder. For every running copy of the executable, the agent:

  1. notes its full command line and the Windows session (desktop) it runs in,
  2. asks it to close normally, as if its close button were clicked,
  3. ends it if it is still running after StopTimeoutSeconds (default 20),
  4. starts it again in the same session, as the same user, with the same command line,
  5. checks that it is still running three seconds later.

Several copies with different parameters each come back with their own parameters. A user must be logged on, at the console or in a disconnected RDP session, for a program to come back on a desktop. On unattended servers use automatic logon, or "StartIn": "Background" when no window is needed.

SecuritySecurity model

ProtectionHow it works
TLS onlyThe agent listens on HTTPS with its own certificate. The app pins its SHA-256 fingerprint on first connect, after you compare it with info, and refuses a different one later.
API keySent in the X-Api-Key header. The agent stores only its SHA-256 hash and compares it in constant time. A wrong key is logged and answered after a 1.5 second delay.
AllowedIpsWhen the list is not empty, only those addresses may connect (loopback is always allowed). Put the IP of the PC that runs CertificateGet here.
Request sizeBodies over 20 MB are refused.
One at a timeDeployments are queued, so two renewals never write the same files at once.

Protect the agent folder

It holds agent.json, the agent's TLS key and the backups, which contain private keys. Keep it readable by administrators or root only. Anyone who can edit agent.json can make the agent run a command as LocalSystem or root.

To rotate the API key, run newkey on the server and paste the new key into every app target that uses the agent.

NotesPlatform notes

Behaviour that belongs to the operating system or to the program receiving the certificate, found while running the agent on real servers.

SELinux and moved binaries

A file moved with mv keeps the SELinux label of the place it came from. A binary moved out of /tmp is labelled user_tmp_t, and systemd fails to start it with status=203/EXEC and no other message. install labels the agent bin_t; after an update copy with cp or run restorecon. The same applies to certificate files you move into place by hand, which is why the Cockpit command runs restorecon -F.

Copying the example file over agent.json

The shipped examples contain placeholders for ApiKeyHash and TlsPassword. The agent survives it: when the TLS password does not open agent-tls.pfx, it renames the old file to agent-tls.pfx.old-<time> and creates a new certificate (the app will ask you to trust the new fingerprint), and check reports the missing key. Copy only the Slots section from an example.

HAProxy loads every file in the crt folder

With crt /etc/haproxy/certs/, HAProxy loads each file in that folder and picks one by SNI. A stray backup or a half-written file there is loaded too, or stops HAProxy from starting. That is why the agent writes atomically and keeps backups elsewhere, and why the reload command runs haproxy -c first.

Cockpit reads the certificate as cockpit-ws

cockpit-tls runs as the cockpit-ws user, so the key (or the combined .cert) must be root:cockpit-ws with mode 640. Cockpit uses the last .cert/.crt file in alphabetical order in /etc/cockpit/ws-certs.d. After several failed starts systemd stops trying, which is why the command runs systemctl reset-failed before restarting the socket.

NetTalk reads its certificate at start-up

A NetTalk web server loads the certificate and key when it starts listening, so new files have no effect until the service or program restarts. Every NetTalk destination therefore needs a RestartServices or RestartPrograms entry.

TSplus needs a password on the PFX

CertificateManager.exe reads the password from certpassword.txt in its own folder and will not import a PFX without one. If the certificate has no PFX password in the app, the agent wraps it with a random password for the import. Both temporary files are deleted afterwards. Versions that use cert.jks expect the keystore password secret, the app's default.

Desktop programs and session 0

The agent runs as a service in session 0, which has no desktop. To bring a program back where the user can see it, it starts it in the user's session with that user's token. With nobody logged on there is no such session, and the program can only be started with "StartIn": "Background".
