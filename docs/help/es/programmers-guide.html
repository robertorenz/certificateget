ValidaciónElegir un método de validación

Antes de emitir, la autoridad de certificación comprueba que usted controla cada nombre, con una solicitud HTTP al dominio o un registro TXT en su DNS. El método se elige para cada certificado en New certificate.

Los comodines necesitan DNS

Un nombre comodín solo se puede demostrar por DNS. Los métodos HTTP se rechazan para certificados comodín.

Validación HTTP

La autoridad de certificación solicita http://<dominio>/.well-known/acme-challenge/<token> en el puerto 80, siempre el 80, desde internet. Con HTTP — built-in web server la aplicación escucha en el puerto 80 de este PC durante los segundos que dura la comprobación; el puerto debe estar libre (detenga IIS o use el método de carpeta del sitio) y redirigido a este PC. Otro puerto solo sirve detrás de una redirección desde el 80. Con HTTP — existing web site folder la aplicación escribe el archivo del token en la carpeta del sitio (ruta local o recurso UNC), añade un web.config para que IIS sirva archivos sin extensión y lo elimina todo al terminar.

Validación DNS

La autoridad de certificación consulta un registro TXT en _acme-challenge.<dominio>. Antes de pedirle que lo compruebe, la aplicación consulta los resolvedores públicos de Settings hasta que todos los registros sean visibles, como máximo durante la espera de propagación (600 segundos de forma predeterminada). Con DNS — manual TXT record usted crea los registros en su proveedor DNS desde el cuadro de diálogo, que tiene botones para copiar y un botón Check DNS now. Borre los registros antiguos después de la solicitud; cada solicitud usa valores nuevos.

APIs de proveedores DNS

Los métodos con proveedor crean los registros TXT, esperan a que aparezcan y después eliminan solo sus propios valores. Escriba las credenciales en Settings → DNS y use el botón Test que hay junto a ellas.

ProveedorDónde obtener las credencialesNotas

Deje Client IP vacío para detectarla.

acme-dns

acme-dns es un pequeño servidor DNS que solo responde consultas TXT de _acme-challenge. Úselo cuando su proveedor DNS no tenga API o no quiera credenciales DNS en este PC. En la primera solicitud de un dominio la aplicación lo registra y muestra un CNAME que debe crear, por ejemplo _acme-challenge.example.com CNAME 8e5700ea-….auth.acme-dns.io. Ese único CNAME cubre el dominio y su comodín. Después, las renovaciones no requieren cambios de DNS. Los registros aparecen en Settings, con Copy target y Remove.

Use su propio servidor acme-dns en producción

El servidor público auth.acme-dns.io sirve para pruebas. Quien tenga las credenciales de un registro puede obtener certificados para ese dominio, así que en producción ejecute el suyo y escríbalo en Settings → acme-dns server.

Autoridades de certificaciónLet's Encrypt y ZeroSSL

La aplicación obtiene certificados de cualquiera de dos autoridades de certificación ACME, elegida para cada certificado en Certificate authority de la página New certificate. El valor predeterminado para certificados nuevos se fija en Settings. Ambas emiten certificados gratuitos y de confianza, válidos 90 días, para un nombre, varios nombres o comodines.

Elija Let's Encrypt cuando quiera probar primero una configuración nueva en Staging. Elija ZeroSSL cuando haya alcanzado un límite de Let's Encrypt, quiera ver los certificados en un panel de ZeroSSL o quiera una segunda autoridad de respaldo.

Configurar ZeroSSL

ZeroSSL solo acepta cuentas ACME vinculadas a una cuenta de ZeroSSL. La aplicación obtiene de ZeroSSL las credenciales de vinculación una sola vez, al crear la cuenta ACME de ZeroSSL, de una de estas dos formas:

  • Con una clave de API de ZeroSSL (recomendado). Inicie sesión en zerossl.com, abra Developer, copie la API Access Key y péguela en Settings → ACME accounts → ZeroSSL API key. La cuenta ACME queda vinculada a su cuenta de ZeroSSL, y los certificados que emite aparecen en su panel de ZeroSSL.
  • Solo con el correo de contacto. Deje vacía la clave de API y escriba el correo de contacto en el certificado (o el predeterminado en Settings). ZeroSSL crea una cuenta para esa dirección si no tiene una, o reutiliza la existente.

Después solo se usa la clave de la cuenta ACME guardada en accounts\zerossl.json; la clave de API no se vuelve a leer. Para pasar a otra cuenta de ZeroSSL, cambie la clave o el correo y haga clic en Reset accounts en Settings. Eso también restablece las cuentas de Let's Encrypt; se vuelven a crear automáticamente en la siguiente solicitud, y los certificados emitidos no se ven afectados.

ZeroSSL no tiene servidor de pruebas

Cada solicitud a ZeroSSL emite un certificado real y de confianza. Para probar un método de validación o una configuración DNS nuevos, ejecútelo una vez con Let's Encrypt Staging y luego cambie el certificado a ZeroSSL.

Cambiar un certificado a la otra autoridad

Abra el certificado, haga clic en Renew, cambie Certificate authority y solicítelo. Los archivos nuevos se añaden al historial del mismo certificado, los objetivos de despliegue no cambian, y las renovaciones siguientes usan la última autoridad elegida. Al agente no le importa qué autoridad emitió el certificado: recibe los mismos orígenes en ambos casos. Solo cambia fullchain-root, porque termina en la raíz de esa autoridad.

CertificadosCertificados, emisiones y archivos

Un certificado en la aplicación es una definición: sus nombres, método de validación, autoridad, tipo de clave, contraseña PFX y objetivos de despliegue. Cada solicitud correcta añade una emisión, una carpeta con fecha que contiene los archivos, a su historial. Renew reutiliza la definición; la última emisión es la que se exporta, instala y despliega.

  • Una clave privada nueva en cada emisión. Cada solicitud genera una clave nueva del tipo elegido; nunca se reutiliza una clave.
  • Archivos escritos: los formatos obligatorios (certificado, clave y cadena en PEM), a partir de los cuales se generan las exportaciones y renovaciones, más los formatos marcados en Settings → Files written for new certificates. Cualquier otro formato se puede generar después con Export. La lista completa está en la Referencia.
  • Los nombres de archivo salen del primer dominio, con * escrito como wildcard: wildcard.example.com.pfx.
  • Las opciones de salida de Settings se aplican a las emisiones y exportaciones nuevas: .key PKCS#8 o tradicional, PFX 3DES o AES-256 y la contraseña JKS.

Vencimiento y renovación

La lista y los totales de la parte superior de Certificates cuentan los certificados como válidos, próximos a vencer (dentro de Settings → Warn when a certificate expires within, 30 días de forma predeterminada) o vencidos / no emitidos. La renovación es manual: Renew y luego Renew certificate. La aplicación no se ejecuta en segundo plano ni de forma programada, así que revísela con regularidad, o renueve todos los certificados próximos a vencer cuando la abra. Let's Encrypt ya no envía avisos de vencimiento por correo.

DespliegueObjetivos de despliegue

Un certificado puede tener cualquier número de objetivos. Tras cada emisión o renovación, cada objetivo habilitado con Deploy automatically recibe los archivos nuevos; el resultado aparece en el objetivo y en el registro de actividad. Un objetivo que falla no afecta a los demás ni a la emisión; corríjalo y haga clic en Deploy now.

Objetivos SFTP / SSH

  1. Escriba el Host, el Port (22) y el User, y elija Password o Private key file (con su frase de paso, si la tiene). Ambos se guardan cifrados.
  2. Escriba la Remote folder y los Files to upload: un tipo de archivo y el nombre remoto de cada uno. {domain} en un nombre se convierte en el primer dominio y {name} en el nombre del certificado. Los ajustes predefinidos HAProxy y nginx rellenan una carpeta, los archivos y el comando.
  3. Opcionalmente, un Command to run afterwards, que se ejecuta por SSH con el mismo usuario. El despliegue falla si termina con un código distinto de cero.
  4. Haga clic en Test connection. La primera vez, la aplicación muestra la huella de la clave de host SSH del servidor; confíe en ella y la aplicación rechazará cualquier otra clave. Forget host key la borra tras reconstruir un servidor.

Cada archivo se sube como <nombre>.cg-upload y luego se renombra sobre el anterior, así que el servidor nunca lee medio archivo. Los archivos que contienen la clave privada reciben modo 600 y los demás 644. Los tipos de archivo están en la Referencia.

AlmacenamientoCarpeta del almacén, secretos y registro de actividad

Todo lo que guarda la aplicación está en la carpeta del almacén (Settings → Store folder, predeterminada %LOCALAPPDATA%\CertificateGet\Store): los certificados y su historial, las claves de las cuentas ACME y el registro de actividad. Los ajustes están en %LOCALAPPDATA%\CertificateGet\settings.json. La estructura está en la Referencia.

  • Cifrado con DPAPI de Windows para su usuario de Windows: contraseñas PFX, claves de cuentas ACME, tokens y claves DNS, contraseñas de acme-dns, contraseñas SFTP y frases de paso de claves, claves de API de agentes. Otro usuario de Windows, u otro PC, no puede descifrarlos; la aplicación crea entonces una cuenta ACME nueva y vuelve a pedir los demás secretos.
  • Sin cifrar: las claves privadas de los archivos .key y .pem, como en cualquier servidor web. Mantenga el almacén fuera de carpetas sincronizadas en la nube y legible solo por usted.
  • Registro de actividad: cada solicitud, validación, exportación, instalación, despliegue y error, en activity.jsonl. La página Activity log lo busca y filtra, y exporta a CSV.

Conceptos del agenteSlots, destinos y archivos

Tres niveles describen adónde va un certificado en un servidor.

NivelQué esCantidad habitual
SlotUn certificado tal como lo ve el servidor. Un objetivo de despliegue de la aplicación nombra un slot.Uno por certificado, por ejemplo reddin-wildcard.
DestinoUn programa que usa el certificado: una carpeta y nombres de archivo, o una importación en TSplus, más lo que hay que reiniciar.Uno por instancia de programa.
ArchivoUn origen (el formato, como fullchain) y el nombre de archivo que recibe.De uno a tres por destino.

La aplicación nunca decide carpetas ni nombres de archivo por un agente. Pregunta al agente qué orígenes necesita el slot y envía esos. Cuando añade una instancia de NetTalk o cambia un nombre de archivo, cambia agent.json en el servidor y nada en la aplicación.

Un agente puede tener muchos slots. Dos certificados desplegados en el mismo servidor son dos slots en el mismo archivo, y dos objetivos en la aplicación (uno en cada certificado) que apuntan a la misma URL del agente.

ConceptosCómo se ejecuta un despliegue

El orden importa al escribir comandos, así que aquí está exactamente como lo ejecuta el agente.

1 · Preguntar

La aplicación llama a GET /api/slots/{slot} y obtiene la lista de orígenes que necesita el slot.

↓
2 · Enviar

La aplicación genera esos archivos a partir del certificado emitido y los envía en Base64 a /api/deploy, con la contraseña PFX solo cuando se necesita pfx, p12 o encrypted-key.

↓
3 · Admitir

El agente vuelve a leer agent.json y comprueba AllowedIps y la clave de API. Los despliegues se ejecutan de uno en uno.

↓
4 · Escribir

Para cada destino, en orden: respalda el archivo actual y escribe el nuevo de forma atómica. Los destinos TSplus importan en su lugar.

↓
5 · Servicios

Cada entrada RestartServices de los destinos correctos, cada servicio una vez, en el orden en que aparece por primera vez.

↓
6 · Programas

Cada entrada RestartPrograms (Windows), cada ejecutable una vez.

↓
7 · Comandos

Los Commands de cada destino en orden, con {folder} sustituido, y después los Commands del propio slot.

↓
8 · Informar

Cada paso, bueno o malo, vuelve al registro de actividad de la aplicación y a agent.log.

Los comandos se ejecutan después de todos los reinicios

Los Commands de un destino no se ejecutan justo después de escribir sus archivos; se ejecutan cuando todos los destinos se han escrito y todos los servicios se han reiniciado. Si un comando debe ir antes de un reinicio, deje RestartServices vacío y haga ambas cosas en un solo comando, por ejemplo icacls … && net stop X && net start X.

Cuando un paso falla

Un paso fallido no detiene el despliegue. Si falla la escritura de un destino, se omiten los reinicios y comandos de ese destino y los demás destinos continúan. Un reinicio fallido o un comando con código de salida distinto de cero se notifica, y el paso siguiente se ejecuta igualmente. El despliegue queda marcado como fallido en la aplicación, con todos los pasos listados, para que pueda ver qué parte funcionó.

ConceptosEditar agent.json en un servidor en producción

El agente vuelve a leer agent.json en cada solicitud. Un slot, destino o nombre de archivo nuevo se aplica al siguiente despliegue sin reiniciar. Solo Port se lee al arrancar; después de cambiarlo, reinicie el servicio y abra el nuevo puerto en el firewall.

Un error de sintaxis no detiene el servicio. Las solicitudes se rechazan con un mensaje claro, que la aplicación muestra, hasta que se corrija el archivo. check muestra la línea:

ERROR agent.json has a syntax error on line 14 (at $.Slots[0].Destinations[0].Folder):
        "Folder": "C:\Apps\Web\certificates",
Common causes: text not inside "quotes", curly quotes instead of straight ", a missing comma between items,
or a comma after the last item. Backslashes in Windows paths must be doubled (C:\\Apps).

ArchivosCómo se escriben los archivos

  • De forma atómica. Cada archivo se escribe en <nombre>.cg-tmp y luego se renombra sobre el anterior, así que un programa nunca lee medio archivo.
  • Las carpetas se crean cuando no existen.
  • Linux, archivos nuevos: el material de clave (combined, combined-keyfirst, encrypted-key, jks, k8s, key, p12, pfx) recibe modo 600; los demás archivos, 644.
  • Linux, archivos reemplazados: conservan el propietario, grupo, modo y etiqueta SELinux del archivo que reemplazan (chown --reference, chcon --reference). Un certificado de Cockpit configurado como root:cockpit-ws 640 se queda así.
  • En Windows los archivos heredan los permisos de la carpeta.

ArchivosCopias de seguridad

Antes de reemplazar un archivo, el actual se copia en la carpeta propia del agente, nunca junto a los archivos en uso. HAProxy carga todos los archivos de su carpeta de certificados, así que un .bak allí también se serviría.

<carpeta del agente>/backups/<slot>/<destino>/<yyyyMMdd-HHmmss>/<archivo>
C:\Program Files\CertificateGet Agent\backups\reddin-wildcard\NetTalk_-_Portal\20260927-031200\portal.crt

KeepBackups (predeterminado 5) es cuántas de esas carpetas fechadas se conservan por destino; 0 desactiva las copias. Para volver atrás, copie los archivos de una carpeta fechada a su sitio y reinicie el programa, o ejecute a mano el comando del destino.

ReiniciosServicios, programas y comandos

RestartServices

En Windows, el servicio se detiene (esperando hasta 90 segundos) y luego se inicia (esperando hasta 90 segundos a que esté Running). En Linux, el agente ejecuta systemctl restart <unidad>. Cada nombre se reinicia una sola vez por despliegue, aunque lo incluyan varios destinos.

Recargue en lugar de reiniciar cuando pueda

Un reinicio corta las conexiones abiertas. Para HAProxy y nginx, deje RestartServices vacío y use una entrada Commands que compruebe la configuración y recargue, por ejemplo haproxy -c -f /etc/haproxy/haproxy.cfg && systemctl reload haproxy.

RestartPrograms

Para programas que se ejecutan en un escritorio en lugar de como servicio, como un servidor NetTalk iniciado desde la carpeta Inicio. Para cada copia en ejecución del ejecutable, el agente:

  1. anota su línea de comandos completa y la sesión de Windows (escritorio) en la que se ejecuta,
  2. le pide que se cierre normalmente, como si se hiciera clic en su botón de cerrar,
  3. lo termina si sigue en ejecución tras StopTimeoutSeconds (predeterminado 20),
  4. lo vuelve a iniciar en la misma sesión, como el mismo usuario, con la misma línea de comandos,
  5. comprueba que sigue en ejecución tres segundos después.

Varias copias con parámetros distintos vuelven cada una con sus propios parámetros. Para que un programa vuelva a un escritorio, debe haber un usuario con sesión iniciada, en la consola o en una sesión RDP desconectada. En servidores desatendidos use el inicio de sesión automático, o "StartIn": "Background" si no hace falta ventana.

Proteja la carpeta del agente

Contiene agent.json, la clave TLS del agente y las copias de seguridad, que incluyen claves privadas. Manténgala legible solo por administradores o root. Quien pueda editar agent.json puede hacer que el agente ejecute un comando como LocalSystem o root.

Para rotar la clave de API, ejecute newkey en el servidor y pegue la nueva clave en cada objetivo de la aplicación que use el agente.

NotasNotas de plataforma

Comportamiento propio del sistema operativo o del programa que recibe el certificado, descubierto al usar el agente en servidores reales.

SELinux y binarios movidos

Un archivo movido con mv conserva la etiqueta SELinux del lugar de origen. Un binario movido desde /tmp queda etiquetado user_tmp_t, y systemd no lo inicia, con status=203/EXEC y ningún otro mensaje. install etiqueta el agente como bin_t; tras una actualización copie con cp o ejecute restorecon. Lo mismo vale para archivos de certificado que coloque a mano, por eso el comando de Cockpit ejecuta restorecon -F.

Copiar el archivo de ejemplo sobre agent.json

Los ejemplos incluidos contienen marcadores para ApiKeyHash y TlsPassword. El agente lo soporta: cuando la contraseña TLS no abre agent-tls.pfx, renombra el archivo antiguo a agent-tls.pfx.old-<hora> y crea un certificado nuevo (la aplicación le pedirá confiar en la nueva huella), y check informa de la clave que falta. Copie de un ejemplo solo la sección Slots.

HAProxy carga todos los archivos de la carpeta crt

Con crt /etc/haproxy/certs/, HAProxy carga cada archivo de esa carpeta y elige uno por SNI. Una copia de seguridad olvidada o un archivo a medio escribir allí también se carga, o impide que HAProxy arranque. Por eso el agente escribe de forma atómica y guarda las copias en otro lugar, y por eso el comando de recarga ejecuta primero haproxy -c.

Cockpit lee el certificado como cockpit-ws

cockpit-tls se ejecuta como el usuario cockpit-ws, así que la clave (o el .cert combinado) debe ser root:cockpit-ws con modo 640. Cockpit usa el último archivo .cert/.crt en orden alfabético de /etc/cockpit/ws-certs.d. Tras varios arranques fallidos systemd deja de intentarlo, por eso el comando ejecuta systemctl reset-failed antes de reiniciar el socket.

NetTalk lee su certificado al arrancar

Un servidor web NetTalk carga el certificado y la clave cuando empieza a escuchar, así que los archivos nuevos no tienen efecto hasta que se reinicia el servicio o el programa. Por eso todo destino NetTalk necesita una entrada RestartServices o RestartPrograms.

TSplus necesita una contraseña en el PFX

CertificateManager.exe lee la contraseña de certpassword.txt en su propia carpeta y no importa un PFX sin ella. Si el certificado no tiene contraseña PFX en la aplicación, el agente lo envuelve con una contraseña aleatoria para la importación. Ambos archivos temporales se eliminan después. Las versiones que usan cert.jks esperan la contraseña de almacén secret, la predeterminada de la aplicación.

Programas de escritorio y la sesión 0

El agente se ejecuta como servicio en la sesión 0, que no tiene escritorio. Para devolver un programa donde el usuario pueda verlo, lo inicia en la sesión del usuario con el token de ese usuario. Si nadie ha iniciado sesión no existe tal sesión, y el programa solo puede iniciarse con "StartIn": "Background".
